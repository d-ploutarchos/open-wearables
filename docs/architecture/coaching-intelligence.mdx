---
title: "Coaching Intelligence"
description: "Query provider-neutral strength and running progression signals for AI coaching agents."
---

Open Wearables turns normalized strength sets and measured running segments into deterministic coaching signals. This interpretation is calculated in the backend so every authorized agent receives the same evidence rather than independently guessing from raw workout payloads.

## Progress endpoint

```http
GET /api/v1/users/{user_id}/coaching/progress
```

Optional query parameters:

- `exercise_id` — restrict strength results to one stable exercise identity
- `distance_meters` — restrict running results to one standard distance
- `window_days` — recent and comparison window length, from 7–365 days; default 42
- `plateau_attempts` — completed sessions or attempts since the best performance before a plateau signal; default 3

Strength results include latest and best estimated 1RM, change from the first eligible session, latest load and volume, recent versus previous average volume, and sessions/days since the best result. Running results include latest and best measured time, time saved versus the first eligible attempt, and attempts/days since the best result.

## Status semantics

- `new` — only one eligible session or attempt exists
- `progressing` — a strict new best occurred in either of the two latest eligible attempts
- `maintaining` — performance remains near its established history without meeting the plateau rule
- `plateau` — the configured number of eligible attempts have occurred since the last best result
- `inactive` — no eligible session or attempt exists inside the selected recent window

These labels are conservative evidence summaries, not medical findings or prescriptive training decisions. An agent should combine them with recovery, sleep, recent training load, injuries, goals, and user feedback before making a recommendation.

## MCP access

Use `get_coaching_progress` for questions such as:

- “How is my squat developing?”
- “Have I plateaued on bench press?”
- “How has my 5K performance changed?”
- “Which lifts have stalled recently?”

Exercise names are resolved to stable, provider-specific exercise identities. If multiple variants match, the tool asks the caller to select the intended exercise instead of merging unlike movements.

## Training-load endpoint

```http
GET /api/v1/users/{user_id}/coaching/training-load
```

The default response compares the latest rolling 7 days with both the previous 7 days and the preceding 28-day baseline. `window_days` can be 3–28 days and `baseline_days` can be 14–180 days.

The response intentionally keeps unlike measurements separate:

- total workout duration in minutes
- eligible external strength volume in kilograms
- running distance in kilometers
- primary-muscle work sets, sessions, and volume
- sleep, recovery, readiness, resilience, body-battery, and strain score context when available

Each workload metric includes current and previous values, a baseline normalized to the selected recent-window length, percentage change, and a `recent_to_baseline_ratio`. Direction labels are `no_load`, `new_load`, `below_baseline`, `within_baseline`, `above_baseline`, or `spike`.

When at least seven paired days are available, `load_health_correlations` compares daily workout duration, strength volume, and running distance with the following day's health score. It returns the Pearson coefficient, direction, strength, sample count, and explicit one-day lag. Missing or zero-variance series are omitted.

<Warning>
  A workload ratio describes change in recorded training; it is not an injury-risk prediction. A health-score change is contextual and does not establish that training caused the change.
</Warning>

Use the MCP tool `get_training_load` for questions such as:

- “How does this week compare with my normal training?”
- “Did my running load spike?”
- “Which muscle groups have I trained recently?”
- “How does my recent sleep look alongside my workload?”

## Proactive coaching events

Bionic can notify an agent without waiting for the user to ask a question. The backend evaluates each user at approximately 08:10 in the user's latest recorded UTC offset and emits two user-scoped outgoing webhook types:

- `coaching.weekly_review.created` — emitted on Monday with the complete training-load and coaching-progress evidence packages
- `coaching.load_alert.created` — emitted when at least two load metrics spike, one metric reaches 1.75× its baseline, or elevated load coincides with an 8-point-or-greater decline in sleep/recovery context

Stable Svix event IDs limit each weekly review to one event per ISO week and each load alert to one event per local calendar day, including after retries or scheduler restarts. A Monday weekly review suppresses a same-morning load alert so the agent sends one consolidated message. Recovery decline alone does not emit this event because sleep webhooks already provide the morning recovery trigger.

The events intentionally contain structured evidence rather than generated advice. The receiving agent applies its own coaching prompt, goals, constraints, conversation history, and delivery channel. Every payload includes an `evidence_policy` warning against causal, diagnostic, or injury-risk claims.

Preview the event decision without sending anything:

```http
GET /api/v1/users/{user_id}/coaching/proactive-preview
```

The preview returns the effective local date and UTC offset, whether a weekly review is due, and the exact weekly-review or load-alert payload that would be emitted. If no recent record has a timezone offset, scheduling falls back to UTC.
